### 📌 개략적 규모 추정
- 주변 친구: 5마일(8km) 반경 이내 친구
- 30초 주기로 위치 갱신
  - 왜? 사람이 걷는 속도가 시간당 3 ~ 4 마일(4 ~ 6k/h) 라서 30초 주기도 해도 크게 검색 결과가 달라지지 않음
- 평균적으로 매일 1억명 사용
- 동시 접속 사용자는 DAU 의 10%
- 한 사용자는 평균적으로 400명의 친구를 갖고, 모두가 주변 친구 검색 기능을 사용
- 앱은 페이자당 20명의 주변 친구를 표시하고 요청이 있으면 더 보여준다.

[QPS]
- 동접자 수는 DAU 의 10%
- 30초마다 갱신 
- ===> QPS = 10,000,000 / 30 = 334,000

## 개략적 설계안 제시 및 동의 구하기
위치 정보를 모든 친구에서(push)해야 한다는 요구사항 때문에 클라이언트와 서버 사이으 통신 프로토콜로 단순한 HTTP 프로토콜을 사용하지 못하게 될 수도 있음을 감안

❓ push 한다는 말을 봐서는 socket 을 말하는거 같은데

### 📌 개략적 설계
이론적으로 순수한 P2P(peer-to-peer) 방식으로도 해결 가능하다.

[p2p 도면]

모바일 단말은 통신 연결 상태가 좋지 않은 경우도 있고, 전력 문제도 있어서 실용적인 해결 방법은 아니지만 설계 방향에대한 통찰을 얻기에는 충분하다.

[공용 백엔드 도면]

더 실용적인 설계안은 고용 백엔드를 사용하는 것이다.  
백엔드 서버의 역할은 아래와 같다.

- 모든 활성 상태 사용자의 위치 변화 내역을 수신한다.
- 위치 데이터를 수신할 때마다 모든 활성 상태 친구를 찾아서 그 친구들의 단말로 변경 내역을 저장한다.
- 두 사용자 사이의 거리가 특정 임계치보다 먼 경우 변경 내용을 저장하지 않는다.

설계 내용만 보면 간단하지만 큰 규모를 가정했을 때 적용이 쉽지 않다.  
계산한 QPS 기준으로 30초마다 초당 334,000 번의 위치 정보를 갱신해야한다.  
평균적으로 1명은 400명의 친구를 갖고, 10% 의 친구가 활성중이라고 한다면 334,000 * 400 * 0.1 = 1,400만 건의 위치 정보 갱신 요청을 처리하고 사용자 단말로 보내야 한다.

### 📌 로드밸런서
RESTful API 서버 및 유상태(stateful) 웹소켓 서버 앞단에 위치한다.  
부하를 분산하기 위해 트래픽을 서버들에 배분하는 역할

### 📌 RESTful API 서버
무상태(stateless) API 서버의 클러스터로서, 통상적인 요청/응답 트래픽을 처리한다.  
친구를 추가/삭제하거나 사용자 정보를 갱신하는 등 부가적인 처리한다.

[요청 흐름 도면]

### 📌 웹소켓 서버
친구 위치 정보 변경을 거의 실시간에 가깝게 처리하는 유상태 서버 클러스터다.  
각 클라이언트는 그 가운데 한 대와 웹소켓 연결을 지속적으로 유지한다.  
검색 반경 내 친구 위치가 변경되면 이 연결을 통해 클라이언트로 전송된다.  
웹소켓 서버는 주변 친구 기능을 이용하는 클라이언트의 초기화도 담당한다.  

### 📌 레디스 위치 정보 캐시
활성 상태 사용자의 가장 최근 위치 정보를 캐시하는 데 사용한다.  
TTL(Time-To-Live) 시간이 지나면 비활성화한다.

### 📌 사용자 데이터베이스
사용자 데이터 및 친구 관계 정보를 저장

### 📌 위치 이동 이력 데이터베이스
사용자의 위치 변동 이력을 보관

### 📌 레디스 pub/sub 서버
초경량 메세지 버스(message bus)로 수백만 개의 채녈(토픽) 이 생성 가능하다.

[레디스 펍/섭 도면]

1. 사용자의 위치 정보 변경 이벤트는 해당 사용자에게 배정된 pub/sub 채널에 발행한다.
2. 각 핸들러는 위치 변경 이벤트를 수신할 친구가 활성 상태변 거리를 다시 계산한다.
3. 새로 계산한 거리가 검색 반경 이내면 갱신된 위치와 시간을 웹소켓 연결을 통해 해당 친구의 클라이언트 앱으로 보낸다.

사용자의 친구 각각과 연결된 웹소켓 핸들러는 해당 채널의 구독자로 설정되어있기 때문에 메세지를 받는다.

### 📌 주기적 위치 갱신

[주기적 위치갱신 흐름 도면]

3 ~ 5 단계는 병렬 실행

1. 모바일 클라이언트가 위치 변경을 LB 에 전송
2. 변경 내역을 웹소켓 서버로 전송
3. 위치 이동 이력을 DB 에 저장
4. 새 위치 정보를 캐시에 저장
   - TTL 갱신
   - 거리 계산
5. 웹소켓 서버는 Redis Pub/Sub 서버로 새로운 위치 발행
6. 발행된 위치를 모든 구독자에게 브로드캐스트(Broadcast)
7. 메세지를 받은 웹소켓은 발행자와 구독자의 거리를 계산한다.
8. 유효한 거리인 경우 구독자에게 새 위치 및 이동이 발생한 시각을 타임스탬프로 해당 구독자의 클라이언트 앱으로 전송

[ 위치 변경 내역 전송 흐름 도면 ]

1. 웹소켓 서버로 위치 변경 내역 전송
2. Redis pub/sub 서버 해당 사용자 전용 채널로 발생
3. 채널을 구독하는 모든 구독자들에게 브로드캐스트
4. 유효한 거리 반경의 친구(구독자)에게 새로운 위치 데이터 전송

### 📌 API 설계

[서버]
1. 주기적인 위치 정보 갱신
- 요청: 위도, 경도, 시간
- 응답: 없음
2. 웹소켓 초기화
- 요청: 위도, 경도, 시간
- 응답: 클라이언트의 친구들 위치 데이터 수신

[클라이언트]
1. 갱신된 친구 위치 정보 수신
- 친구 위치 데이터와 시간(타임스탬프) 수신
2. 새 친구 구독
- 요청: 웹소켓 서버는 친구 ID 전송
- 응답: 최근 위도, 걍도, 시간
3. 구독 해지
- 요청: 웹소켓 서버는 친구 ID 전송
- 응답: 없음

친구를 추가/삭제 하거나 사용자 정보를 갱신하는 기본 API 제외

#### 위치 정보 저장에 DB를 사용하지 않는 이유
사용자의 '현재 위치' 만 이용하는 서비스이기 때문에 하나만 저장하는걸로 충분하고, 레디스는 읽기 및 쓰기 연산 속도가 빠르기 때문에 이런 목적에 적합하다.  
TTL 을 지원해 활성 상태를 자동으로 제거할 수 있고, '주변 친구' 기능의 위치 정보가 영속성을 보장할 필요가 없다.
  
장애가 발생하는 경우에 새로운 서버가 warmed up 되는 시간에 갱신 주기가 경과하는 경우가 생길 수 있지만 수용 가능한 문제로 본다.
  
#### 위치 이동 이력 DB

user_id latitude longitude timestamp

- 책에서는 수평적 확장이 가능한 Apache Cassandra(NoSQL) 가 부합하다고함
- RDB 도 샤용 가능하나 이력 데이터 양이 서버 한 대로 힘들어서 샤딩(Sharding) 이 필요하다함

## 3단계: 상세 설계

### 📌 중요 구성요소별 규모 확장성

#### API 서버
클러스터의 규모를 CPU 사용률이나 부하, I/O 상태에 따라서 자동으로 늘리는 방법이 다양하기 때문에 특별하게 다루지는 않음

#### 웹소켓 서버
자동으로 늘리는 것은 API 서버와 마찬가지지만 유상태 서버라서 기존 서버를 제거할 때 주의가 필요하다.  
LB 에서 먼저 상태를 '연결 종료중(Draining' 으로 변경하고 충분한 시간이 흐른 뒤 서버를 종료하면된다. (새로운 연결이 만들어지지 않도록)

⚠️ 유상태 서버 클러스트의 큐모를 자동으로 확장하려면 LB 가 필요하다.  
❓ 그러면 축소도 필요한거 아닌가?

#### 클라이언트 초기화
웹소켓 서버와 클라이언트가 '지속성 연결'을 하는데 오늘날 연결 유지에 많은 메모리를 필요로 하지 않는다.  
  
웹소켓 연결이 초기화되면 모바일 단말의 위치가 전송되고 그 정보를 웹소켓 서버가 다음 작업을 수행하기 위해 사용한다.

1. 사용자 위치 정보 캐싱
2. 위치 정보를 거리 계산에 사용하기 떄문에 연결 핸들러 내의 변수에 저장
❓ 연결 핸들러는 어떤걸까? 파일이라서 그 내부에 변수로 저장하는건가?
3. DB 통해서 사용자 친구 목록 조회
4. 위치 정보 캐시에 일괄(batch) 요청을 보내 모든 친구의 위치를 가져온다.(TTl 서정 해놓으니 비활성화 친구는 캐시에 없을것)
5. 사용자와 친구들 사이의 거리를 각각 계산해 검색 반경 이내면 친구의 상세 정보, 위치 그리고 시각을 클라이언트에 반환
6. 웹소켓 서버는 각 친구의 레디스 서버(pub/sub) 채널을 구독 
- 채널 비용이 생성 및 구독 비용이 저렴해 모든 친구 채널을 구독해도 괜찮다.
- 비활성화 상태 친구의 채널을 유지하는건 메모리가 소비되지만 소량이고, 활성화 상태 전까지 CPU 나 I/O 가 없기 때문에 무시
7. 사용자의 현재 위치를 레디스 pub/sub 통해 모든 친구에게 전송한다.

#### 사용자 DB
저장하는 데이터
- 사용자 상세 정보(Profile)
- 친구 관계

지금 설계 하고자하는 시스템의 데이터 규모는 한 대의 RDB 로는 감당할 수 없어 샤딩을 통한 수평적 규모 확장이 필요하다.  
직접 질의하는 대신 내부 API 를 통해서 대이터를 가져오는데 시스템 성능상 큰 차이는 없을 것이다.


#### 위치 정보 캐시
각 항목의 키에는 TTL 을 사용하는데 사용자 위치 정보가 갱신될 때마다 초기화된다. (=메모리 한도는 일정 한도 아래로 유지됨)  
시스템이 붐비다는 가정하에 10,000,000 만명이 활성화 상태이고 한 사람의 데이터가 100byte 필요하다 했을 때 수 GB 데이터를 레디스 한 대로 캐싱할 수 있다.  
  
하지만 30초마다 활성 사용자가 갱신되기 때문에 레디스 서버가 갱신 연산의 수는 초당 334K 에 달하게되어 부담이 커지게 되는데 캐시할 데이터 또한 사용자 ID 기준으로 샤딩을 통해서 여러 서버에 부하가 고르게 분배할 수 있다.
가용성을 높히고 싶다면 대기(standby) 노드에 복제해 두었다가 주(Primary) 노드 장애 발생시 대기 노드를 주 노드로 승격 시키면 장애 시간이 줄어든다.

#### 레디스 pub/sub
이 설계안에서 pub/sub 은 위치 변경 내역 메세지를 라우팅(routing) 하는 하나의 계층으로 활용한다.  
 
- '주변 친구' 기능을 활용하는 모든 사용자에게 채널 하나씩 부여
- 초기화시 모든 친구의 채널의 채널과 구독 관계 설정 (상태 무관)

비활성 된 친구의 채널을 구독 중단하고, 활성된 상태로 변경된 친구의채널을 구독하는 작업을 하지 않기 때문에 더 많은 메모리를 사용하여 메모리 병목이 생길 가능성은 있다.

### 📌 얼마나 많은 Redis pub/sub 서버가 필요한가?

#### 메모리 사용량
해당 기능을 사용하는 모든 사용자에게 채널을 하나씩 부여하니까 10,000,000 개의 채널이 생성되고 활성화 상태 친구들중 100명이 해당 기능을 사용한다고 가정했을 떄 구독자 한 명을 추적하기 위해서 내부 해시 테이블과
연결 리스트에 20 byte 상당의 포인터를 저장한다.  

100,000,000 * 100 * 20 = 200GB
  
100GB 메모리를 설치할 수 있는 버전이면 모든 채널을 보관하는데 두 대의 서버가 필요하다.

❓어떤 기준으로 20 byte 가 되는거지? 3개의 포인터면 24 byte 아닐까 싶은데 (책은 20 byte 상당이라고 말함)

#### CPU 사용량
pub/sub 서버가 구독자에게 전송해야 하는 위치 정보 업데이트의 데이터 양은 1,400만 건에 달한다.  
보수적으로 기가비트 네트워크를 탑재한 현대 아키텍처 서버 한 대로 감당 가능한 구독자 수는 100,00 이라고 가정한다.  

14,000,000 / 100,000 = 140 대

보수적인 결과 값이고 실제로 필요한 숫자는 훨씬 적을 것이다.

- 레디스 pub/sub 의 병목은 메모리가 아니라 CPU 사용량이다.
- 설계안에서 다루는 규모를 감당하려면 분산 레디스 pub/sub 클러스터가 필요하다.

#### 분산 Redis pub/sub 서버 클러스터
수백 대의 레디스 서버에 채널을 분산할 방법은 무엇인가?  
모든 채널은 독립적이기 때문에 메세지를 발행할 사용자 ID를 기준으로 Pub/Sub 서버들을 샤딩하면 된다.  

1. 가용한 서버 목록을 유지하는 기능 및 해당 목록을 갱신하는 소규모 키-값 저장소라고 보고 진행한다.
- key: /config/pub_sub_ring
- val: ["p_1", "p_2", "p_3", "p_4"]

2. 웹소켓 서버(클라이언트) => 레디스 Pub/Sub 에서 발생한 변경 내역을 구독할 수 있도록

[channel_assignment.svg]

웹소켓 기준으로는 채널에 위치 정보 변경 내역을 발행하는 과정은 어떻게 되나?

1. 웹소켓 서버는 해시 링을 참조해 레디스 Pub/Sub 채널을 선정한다.  
   효율을 높이고 싶다면 웹서버에 해시 링 사본을 캐싱하는 것도 고려할 수 있다.(동기화 유지 고려)
2. 위치 정보를 발행한다.

### 📌 레디스 Pub/Sub 서버 클러스터 규모 확장 고려사항

1. Redis Pub/Sub 서버는 채널 구독자에게 전송되고나면 메모리나 디스크에 메모리에 메세지를 저장하지 않는 무상태 서버라고 할 수 있다.
2. 하지만 구독자 목록은 핵심 정보이기 때문에 해시 링에서 제거하는 경우 다른 채널로 이동하고, 해당 채널을 구독하는 구독자에게도 그 사실을 알려야한다.
   이러한 관점에서 Pub/Sub 서버는 유상태 서버이다.

유상태 서버 클러스터의 규모를 늘리거나 줄이는 것은 운영 부담과 위험이 큰 작업이다.  

- 클러스터를 조정하면 채널들이 해시링의 다른은 서버로 이동하는데 해시링 갱신에 따른 재구독 요청 발생이 몰린다.
- 재구독 요청을 처리하다가 사용자 정보 변경 메세지 처리가 누락될 수 있다.
- 하루 중 시스템 부하가 가장 낮을 때 클러스터 조정하는게 좋다.

어떻게 조정할까?

1. 새로운 링 크기를 계산 => 새 서버 준비
2. 해시 링에 매달린 값을 새로운 내용으로 갱신한다.
3. 모니터링
