2차원 평면 공간으로 표현된 지리적 영역 위의 격자를 더 작은 격자로 재귀적으로 분할해 나가는 방법

### 📌 경로 안내 알고리즘을 위한 도로 데이터 처리

경로 탐색 알고리즘 Dijkstra 혹은 개량된 A* 알고리즘  
그래프 탐색 알고리즘이라서 그래프가 필요한데 교차로를 노드(node), 도로는 간선(edge) 로 표현하는 그래프 자료 구조를 가정한다.  
각 격자의 도로망을 그래프로 변환하고, 이를 경로 안내 타일(routing tile) 이라 부른다.
각 타일은 도로로 연결된 다른 타일에 대한 참조(reference) 를 유지한다.
(지도는 png, 경로 안내 타일은 이진 파일(binary file))

### 📌 계층적 경로 안내 타일

타일의 구체성을 상/중/하 로 구분하여 타일간 표현 가능한 정보를 나눈다.

- 상: 지방도(local roads)
- 중: 큰 관할구(district)
- 하: 도시와 주를 연결하는 주요 고속도로 데이터

### 📌 저장소 사용량

#### 세계 지도
세계 지도를 21번 확대 한다고 했을 때 4.4개의 타일이 필요하다.  
한 장의 타일이 256 x 256 픽셀 압축 PNG 파일이라면 한 장당 100KB 저장 공간이 필요하다. (4.4조 x 100KB = 440PB)

지구상에 인간이 살 수 있는 공간이 10 ~ 20% 인거를 감안하면 88PB 정도고 책에서는 어림잡아 50PB 로 진행한다.  
확대 수준이 내려가면 필요한 타일 수는 1/4 줄어들기 때문에

50 + 50/4 + 50/16 ... = ~67BP 정도이기 때문에 대략 100PB 라고 생각한다.

### 📌 서버 대역폭

- 안내 세션 시작 메세지 전송
- 위치 갱신 요청

```
DAU: 10억
평균적으로 주당 35분 이용

10억 x 35분 = 350억분
(= 하루 50억분)

GPS 가 매 초 전송한다고 했을 때  50억분을 초로 환산히면
50억분 x 60초 = 3000억 요청

QPS: 3000억 / 10^5 = 300백만
```

매 초 요청을 보내면 서버에 부하가 오기 때문에 클라이언트에 모아 두었다가 한 번에 보내는 방법을 사용하면 QPS 를 낮출 수 있다.

```
15초 기준으로 모아둔다고 가정하면

QPS: 300백만 / 15 = 20만
```

## 2단계: 개략적 설계안 제시 및 동의 구하기

### 📌 위치 서비스
클라이언트가 t촉마다 자기 위치를 전송한다고 가정 (주기적 데이터 전송)

- 데이터 스트림을 활용
    - 실시간 교통 상황
    - 오픈, 폐쇄 도로 탐지
    - 사용자 행동 애ㅑㅑㅇ태 분석
- 실시간 정보에 가까워 ETA 정확성 향상

### 📌 지도 표시
클라이언트가 모든 데이터를 가지고 있는 건 실용적이지 않으니 타일을 서버에서 가져오는 접근법이 바람직하다.

언제?
- 확대 및 이동으로 지도 탐색 시
- 경로 안내 시 타일을 벗어나 인접 타일로 이동 시

방법1) 클라이언트가 보는 지도를 즉석에서 타일을 만들기 (조합이 무한히 나옴)
- 모든 타일을 동적으로 만들어 서버 클러스터에 부하
- 캐시 사용이 불가능함

방법2) 정적인 방법으로 지오해싱 같은 분할법으로 미리 만들어 두고 사용자 확대 수준에 근거해서 지도 타일 집합을 결정한다.  
지오해시 URL로 변환 -> CDN을 통해 서비스

[ 사용자 - CDN - DB ]

CDN을 통해서 지도 타일을 조달하고 CDN에 없는 경우 원본 서버에서 가져온다.

- 원본에 다시 접촉하지 않음
- 규모 확장에 용이
- 정적이기 때문에 캐시 사용

[ CDN 사용 안 한 서버와 사용 구조 차이 ]

200m x 200m(256px x 256px) 영역의 타일이라고 가정하고, 용량은 100KB라고 가정하고 1km x 1km 영역을 표현하려면 2.5MB가 필요하고  
사용자가 30km/h로 이동할 때 30 x 2.5MB는 75MB이다. (분당 1.25MB)

※ CDN 트래픽 규모는 어느 정도 될까?  
책에서는 50억 '분(minutes)'을 가정했으니까 50억 x 1.25MB = 6.25PB가 하루에 전송되는 양인데 이는 초당 62,500MB나 된다.  
하지만 CDN을 사용한다고 했을 때 전 세계에 200개의 서버가 있다면 62,500 / 200 = 312.5MB 정도 된다.

[ 지도 표시 흐름도 ]

1. 모바일 사용자가 타일 URL들을 요청
2. LB가 요청을 타일 서비스 서버로 전달
3. 클라이언트 확대 수준 기반으로 9개의 타일 URL을 계산해 반환 (주변 타일까지)
4. 클라이언트는 CDN을 통해서 다운로드

## 상세 설계

### 📌 데이터 모델

#### 경로 안내 타일
외부에서 받는 도로 데이터는 가공되지 않은 데이터이기 때문에 경로 안내에 그대로 사용할 수 없다.  
오프라인 데이터 가공 파이프라인을 주기적으로 실행해서 변경 사항들을 반영해 줘야 한다.  
해상도별로 경로 안내 타일 3벌을 만들고, 각 타일들에는 그래프의 노드와 선분으로 표현된 해당 지역 내 교차로와 도로 정보가 들어 있다.

또 그래프 데이터도 메모리에 위치할 수 없기 때문에 효율적인 방법으로 S3 같은 객체 저장소에 보관하고 경로 안내 서비스에 캐싱하는 게 좋다.  
(인접 리스트를 이진 파일 형태로 직렬화해 주는 소프트웨어 패키지 이용)

### 📌 사용자 위치 데이터
도로 데이터 및 경로 안내 타일을 갱신하는 데 사용되고, 실시간 교통 상황이나 이력을 갖는 DB 구축을 할 수 있는 값진 데이터다.  
위치 데이터를 처리하여 지도 데이터를 갱신할 데이터 스트림 프로세싱 서비스도 필요  
데이터 규모가 크기 때문에 대량의 쓰기 연산이 가능해야 하고 수평적 규모 확장이 가능한 DB가 필요하다.

### 📌 지오코딩 데이터베이스
주소를 위도/경도 쌍으로 변환하는 정보를 갖는다.  
빠른 읽기 연산을 제공하는 key-value 저장소가 적당하다. (읽기 연산은 많고, 쓰기는 적음)

### 서비스

#### 위치 서비스

[ 사용자 위치 데이터베이스 ]

초당 백만 건의 위치 정보 업데이트가 발생하는 걸 감안했을 때 NoSQL 키-값 DB나 열-중심 DB가 요구 사항에 적합하다.  
사용자 위치가 변경되면 이전 데이터는 무용해지기 때문에 일관성보다는 가용성을 우선한다.

- 데이터베이스 키: (user_id, timestamp)
- 파티션 키: user_id
- 클러스터링 키: timestamp => 정렬

#### 사용자 위치 데이터는 어떻게 이용되는가
카프카 같은 응답 지연이 낮고, 많은 데이터를 동시에 처리할 수 있는 데이터 스트리밍 플랫폼으로 실시간 데이터 피드를 제공한다.

- 실시간 교통 상황
- 실시간 교통량 데이터베이스 갱신
- 새로운 곳이나 폐쇄된 도로 탐지

### 📌 지도 표시

#### 지도 타일 사전 계산
확대할 때마다 동서 방향 두 배, 남북 방향 두 배 늘어나서 해상도가 이전 해상도의 4배씩 늘어난다.
해상도는 늘어나지만 클라이언트 입장에서는 타일을 다운로드받는 데 더 많은 대역폭을 사용하는 게 아니라 확대 레벨에 맞는 타일을 다운로드받는 것이기 때문에 대역폭을 소진하지 않고도
최적인 크기의 지도를 표시할 수 있다.

#### 최적화: 벡터 사용
네트워크를 통해서 이미지를 전송하는 게 아니라 아래를 전송하면 클라이언트는 수신된 정보로 지도를 그린다.
(왜? 벡터 타일은 압축률이 높다)

- 경로(path)
- 다각형(polygon)
- 벡터(vector)

### 📌 경로 안내 서비스

#### 최단 경로 서비스

출발지와 목적지의 위도/경도를 입력받아 k개 최단 경로를 반환하는 서비스로 A* 알고리즘 사용
(교통이나 도로 상황은 고려x = 도로 구조에 의존 / 도로망 그래프는 정적이라 캐싱)

#### 예상 도착 시간 서비스
기계 학습을 활용해 현재 교통 상황 및 과거 이력에 근거하여 예상 도착 시간을 계산한다.  
영향을 주는 요소가 많고 알고리즘 차원의 문제

#### 중요 정보 갱신 서비스들
카프카 위치 데이터 스트림을 구독하고 도로 정보를 반영하여 경로 안내 타일을 지속적으로 갱신한다.

#### 적응형 ETA와 경로 변경
경로 안내를 받고 있는 모든 사용자들을 추적하고 교통 상황에 따라 달라지는 ETA를 업데이트해 줘야 한다. (O(NxM))

- 안내받는 사용자들은 어떻게 추적?
- 변한 교통 상황에 영향을 받는 사용자를 효율적으로 식별하는 방법은?

[ 재귀 도면 ]

출발지와 목적지가 모두 포함된 타일을 재귀적으로 찾아 영향을 받는 타일을 식별할 수 있고, 그 이외의 사용자들에게는 영향이 안 가도록 할 수 있다. (O(N))
이런 경우 처리가 필요한 점은 교통 상황이 완화되어서 다시 이용할 수 있을 때 사용자들에게 어떻게 알릴 것인가이다. (ETA를 주기적으로 계산한다면 해결됨)

#### 전송 프로토콜

- 모바일 푸시 알림 (Mobile Push Notification)
    - 메시지 크기가 제한적이다(iOS: 4,096B)
- 롱 폴링 (Long Polling)
- 웹 소켓 (Web Socket)
- SSE (Server-Sent Event)

폴링보다는 웹 소켓이 서버에 주는 부담이 적다.  
웹 소켓이 양방향 통신을 지원하기 때문에 양방향 통신이 필요하다면 채택 가능하다.
