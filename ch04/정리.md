# 분산 메세지 큐

소프트웨어 아키텍처에서 통신과 조율을 담당함

- 결합도 완화(Decoupling)
- 확장성
  - 트래픽이 몰리면 소비자를 추가해서 처리 용량을 늘릴 수 있다
- 가용성
  - 특정 컴포넌트의 장애가 다른 컴포넌트의 장애로 전파되지 않도록 설계가능
- 성능
  - 비동기 통신
  - 생산자, 소비자가 서로 기다리는 병목이 없 

## 1단계: 문제 이해 및 설계 범위 확정

- 생산자(Producer): 메세지를 큐로 전송
- 소비자(Consumer): 큐에서 메세지 읽음

책에서는 면접시 고려사항으로 (이길 기능 요구사항으로 해석)
- 메시지 포맷(Format): 텍스트인지 멀티미디어 지원도 가능한지 물어봄
- 메세지 크기(Size)
- 소비자 여러개가 메세지 접근이 가능한지
- 메세지 생성 순서를 지켜서 보장할지
- 데이터 지속성
- 생성자와 소비자 수
- 전달 방식
  - 최대 한 번(at-most-once)
  - 최소 한 번(at-least-once)
  - 정확히 한 번(exactly once)
- 대역폭(Throughput)
- 단대단(end-to-end)

❓ 정통 MQ 는 이벤트 스트리밍 플랫폼과 달랐지만 지원하는 기능들이 추가되면서 차이가 크게 다르지 않아짐
ex) MQ 는 메세지 소비 순서를 보증하지 않았음

### 📌 비기능 요구사항
- 높은 대역폭과 낮은 전송 지연 가운데 하나를 설정으로 선택 가능하도록
- 이 분산시스템에서 메세지 양이 급증해도 처리 가능하도록
- 지속성 및 내구성: 디스크에 지속적으로 보관되어야 하며 여러 노드에 복제되어야함

## 2단계: 개략적 설계안 제시 및 동의 구하기

### 📌 메세지 모델
가장 널리 쓰이는 모델

- 일대일(point-to-point)
- 발행-구독(publish-subscribe)

#### 일대일 모델

[118. 일대일 모델]

여러 소비자가 있어도 한 메세지는 한 소비자만 가져가능 모델이다. 
책에서의 설계에서는 메세지를 두 주 보관할 수 있는 지속성 계층(Persistence Layer) 를 포함한다.

#### 발행-구독 모델

[119. 발행-구독 모델]

토픽(Topic) 은 메세지를 주제별로 정리하는 데 사용한다.
토픽에 전달된 메세지는 해당 토픽을 구독하는 모든 소비자에 전달된다.

### 📌 토픽, 파티션, 브로커

메세지는 토픽에 보관되는데 데이터의 양이 커진다면?
파티션(Partition), 즉 샤딩(Shading) 기법을 활용 가능하다.

[119. 파티션]

토픽을 여러 파티션으로 분할한 다음에 모든 파티션에 균등하게 나눠 보낸다.
파티션은 메세지 큐 클러스터 내의 서버에 고르게 분산 배치한다.

파티션을 유지하는 서버는 브로커(Broker) 라 부른다.
파티션을 브로커에 분산하는 것이 높은 확장성을 달성하게 해준다.(토픽 용량 확장시 파티션 개수를 늘린다.)

토픽 파티션은 FIFO(first in, first out) 으로 메세지 순서를 유지하고 메세지 위치는 오프셋(offset) 이다.
메세지는 ID와 같은 키를 갖는데 같은 키를 갖는 모든 메세지는 같은 파티션으로 보내진다.
키가 없는 메세지는 무작위 파티션으로 전송된다.

[120. 메세지 큐 클러스터]

토픽을 구독하는 소비자는 하나 이상의 파티션에서 데이터를 가져온다.
토픽을 구독하는 소비자가 여럿인 경우, 각 구독자는 해당 토픽을 구성하는 파티션의 일부를 담당한다.  
소비자들을 해당 토픽의 소비자 그룹이(Consumer Group)라 부른다.

### 📌 소비자 그룹

[120. 소비자 그룹]

하나의 소비자 그룹은 여러 토픽을 구독할 수 있고, 어디까지 읽었는지를 나타내는 오프셋을 그룹마다 따로 관리한다. 같은 그룹 안의 소비자들은
메시지를 병렬로 소비할 수 있다.

하지만 그룹 안의 여러 소비자가 같은 파티션을 동시에 읽으면, 그 파티션의 메시지를 순서대로 소비한다는 보장이 깨진다. 그래서 "하나의 파티션은
그룹 안에서 한 소비자만 읽는다"는 제약을 두어 이 문제를 해결한다. 그림 4.7에서 토픽-B는 파티션이 하나뿐이라, 소비자 그룹-2에서는 소비자-4만
토픽-B를 읽고 소비자-3은 토픽-B의 메시지를 받지 않는다.

결과적으로 그룹 안에서는 메시지 하나를 소비자 한 명만 받는 일대일 모델이 되고, 그룹끼리는 같은 메시지를 각자 모두 받는 발행-구독 모델이
된다. 그래서 이 설계는 두 모델을 모두 지원할 수 있다.

그룹 안에서 동시에 일할 수 있는 소비자 수는 파티션 수를 넘을 수 없다. 파티션보다 많은 소비자는 맡을 파티션이 없어 놀게 된다. 파티션은 가장
작은 저장 단위이므로, 처음부터 파티션을 넉넉히 만들어 두면 나중에 파티션 수를 동적으로 늘리지 않고 소비자만 추가해서 처리 용량을 늘릴 수
있다.

### 📌 개략적 설계안

[ 121. 개략적 설계안 ]

- 클라이언트
  - 생산자: 메세지를 특정 토픽으로
  - 소비자 그룹: 토픽 구독 및 메세지 소비

- 브로커: 파티션을 유지
- 저장소
  - 데이터 저장소: 메세지가 저장되는 곳
  - 상태 저장소: 소비자 상태 저장
  - 메타데이터 저장소: 토픽 설정, 속성 등
- 조정 서비스(Coordination Service)
  - 서비스 탐색(Service Discovery): 어떤 브로커가 살아있는지
  - 리더 선출(Leader Election): 브로커 가운데 하나는 컨트롤러 역할을 담당해야 하며 한 클러스터에는 반드시 활성 상태 컨트롤러가 하나 있어야 한다. (컨트롤러가 파티션 배치 책임)
  - 아파치 주키퍼(Apache ZooKeeper)나 etcd가 보통 컨트롤러 선출 담당

## 3단계: 상세 설계

데이터 장기 보관, 높은 대역폭을 위한 결정

- 회전 디스크(Rotational Disk)의 높은 순차 탐색 성능
- OS 가 제공하는 적극적 디스크 캐시 전략(Aggressive Disk Caching Strategy)을 잘 이용하는 디스크 기반 자료 구조(on-disk Data Structure)
- 데이터의 양이 막대한 경우 메세지 복사에 드는 비용 최소화
- 일괄 처리(Batching) 우선하는 시스템
  - 생산자닌 메세지 일괄 전송
  - 메세지 큐는 메세지를 큰 단위로 묶어 보관
  - 소비자는 메세지 일괄 수신

### 📌 데이터 저장소

- 읽기와 쓰기가 빈번하게 일어남
- 갱신과 삭제 연산은 발생하지 않음

=> 대부분은 순차적 읽기와 쓰기

#### 선택지 1: 데이터베이스

- RDB: 토픽별 테이블 (레코드)
- NoSQL: 토픽별 콜렉션 (문서)

읽기와 쓰기 연산이 동시에 대규모로 발생하기 때문에 DB는 설계가 어렵고, 오히려 시스템의 병목 지점이 된다.

#### 선택지 2: 쓰기 우선 로그(Write-Ahead Log, WAL)
복구 로그(redo log) 가 WAL 로 구현된어 있다고 생각하면 된다.
지속성을 보장해야 하는 메세지는 디스크에 WAL로 보관을 추천
WAL 은 접근 패턴이 읽기/쓰기 전부 순차적이고, 디스크는 접근 패턴이 순차적일 때 좋은 성능을 보인디.

[124. 새로운 메세지 추가]

새로운 메세지가 파티션 꼬리 부분에 추가되며, 오프셋은 점진적으로 증가한다.
가장 쉬운 방법은 로그 파일 줄 번호를 오프셋으로 사용하는 것이다.
파일의 크기가 무한정으로 커질 수 없으니 세그먼트(Segment) 단위로 나누는 것이 좋다.
새 메세지는 활성 상태의 세그먼트 파일에 추가되고, 세그먼트 한계가 도달하면 새 활설 세그먼트 파일이 만들어져 새로운 메세지를 수용하고, 이전에 활성 상태였던 세그먼트는 비활성화 상태로 변한다.
비활성 세그먼트는 읽기 요청만 처리한다. (기한 만료나 용량 한계 도달시 삭제)

### 📌 디스크 성능 관련 유의사
회전식 디스크가 느려지는 것은 데이터 접근 패턴이 무작위(random) 일 때다.

### 📌 메세지 자료 구조
메세지 구조는 높은 대역폭 중요 열쇠다.
메세지가 소비자까지 전달되는 과정에서 불필요한 복사가 일어나지 않도록 하는게 중요하다.
메세지 자료 구조는 생산자 - 메세지 큐 - 소비자 사이의 일종의 계약이다.

아래는 필드 이름, 데이터 자료형 두 개 컬럼의 표
key byte[]
value byte[]
topic string
partition integer
offset long
timestamp long
size integer
crc integer

### 📌 메세지 키
파티션을 정할 대 사용된다.
키는 파티션 번호가 아니며 필요하다면 파티션 선정 매커니즘을 직접 정의할 수 있다.
키가 주어진 경우 파티션은 hash(key) % 파티션 수 공식에 따라서 정해진다.

### 📌 메세지 값
페이로드(payload)를 말한다.
텍스트일 수 있고, 압축된 이진 블록일 수 있다.

⚠️ 유의점
키-값 저장소에서 이야기하는 키와는 다르게 메세지의 키는 고유할 필요가 없다.
메세지에 반드시 키를 두어야 하는것도 아니고, 키를 이용해서 값을 찾는것도 아니다.

### 📌일괄 처리(Batching)
값 비싼 네트워크 왕복 비용을 제거할 수 있다.
한 번에 디스크에 메세지를 기록한다면 순차 쓰기 연산으로 디스크 캐시에 연속된 공간을 점유하면서 디스크 접근 대역폭을 달성한다.

### 📌생산자 측 작업 흐름
메세지를 어느 브로커의 파티션으로 보내야할까?
이 문제를 해결하기 위해서 한 가지 해결책으로 라우팅 계층(Routing Layer)을 도입한다.
이 계층의 역할은 적절한 브로커(리더 브로커)에 메세지를 보내는 역할을 담당한다.

[129. 라우팅 계층]

1. 생산자는 메세지를 라우팅 계층으로 보낸다.
2. 라우팅 계층은 메타데이터 저장소에서 사본 분산 계획(Replica Distribution Plan)을 읽어 캐시에 보관하고 메세지가 도착하면
   파티션-1 리더 사본에 보낸다. (예시)
3. 리더 사본이 우선 메세지를 받고 다른 사본은 해당 리더로부터 데이터를 받는다.
4. 충분한 수의 사본이 동기화되면 리더는 데이터를 디스크에 기록(Commit) 하고 소비자에게 회신을 보낸다. (소비 가능한 시점)

단점
- 라우팅 계층이 하나 더 생기면서 거쳐야 할 네트워크 노드가 더 늘어나 오버헤드가 발생해 네트워크 지연 증가
- 일괄 처리가 가능하면 효율을 높일 수 있는데 고려하지 않음

[130. 수정된 설계안]

라우팅 계층을 생산자 클라이언트 라이브러리로 생산자에 설치해 생산자 내부로 편입하고 버퍼를 도입힌다.

- 네트워크를 거칠 필요가 줄어 전송 지연도 줄어든다.
- 생산자는 메세지를 어느 파티션에 보낼지 결정하는 자신만의 로직을 가질 수 있다.
- 전송할 메세지를 버퍼 메모리에 보관했다가 목적지로 일괄 전송해 대역폭을 늘린다.

[130.일괄 처리 메세지 양 선택]

얼마나 많은 메세지를 일괄 처리하는게 좋을지는 대역폭과 응답 지연 사이에서 타협점을 찾는 문제이다.

### 📌 소비자 측 작업 흐름
소비자는 특정 파티션의 오프셋을 주고 해당 위치에서부터 이벤트를 묶어서 가져온다.

[131. 메세지 흐름]

### 📌 푸시 vs 풀
브로커가 데이터를 소비자에게 보내기 vs 소비자가 가져오기

#### 푸쉬 모델
장점
- 낮은 지연: 브로커는 메세지를 받는 즉시 소비자에게 전송
단점
- 소비자가 메세지를 처리하는 속도가 생산자가 만드는 속도보다 느리면 소비자에 부하
- 생산자가 데이터 전송 속도를 좌우하므로, 소비자는 항상 그에 맞는 처리가 가능한 컴퓨팅 자원 준비

#### 풀 모델
장점
- 메세지 소비 속도를 소비자가 결정히고 실시간으로 소비자가 일괄로 가져가능 구성 가능
- 생산 속도보다 소비 속도가 느리면 소비자를 늘려 해결하거나 생산 속도를 따라잡을 때까지 기다림
- 일괄 처리에 적합: 푸쉬 모델은 소비자가 처리 여건이 되는지 몰라 소비자가 제때 처리하지 못한 메세지는 버퍼에 쌓여 처리를 기다리게 한는데 반면
  풀 모델은 소비자가 마지막으로 가져간 로그 위치 다음에 오는 메세지를 한 번에 가져갈 수 있다.(혹은 설정된 최대 개수 만큼) => 일괄 처리에 적합

단점
- 브로커에 메세지가 없어도 데이터를 끌어가려고 시도해서 소비자측 컴퓨팅 자원이 낭비되는데 이를 위한 롱 폴링(Long Polling) 모드가 지원된다.

[ 132. 풀 모델 ]

그룹-1 에 합류하고 토픽-A 를 구독하길 원하는 소비자가 있다.
그룹 이름을 해싱하여 접속할 브로커 노드를 찾고, 같은 그룹의 소비자는 같은 브로커에 접속한다.
이런 브로커를 해당 소비자 그룹의 코디네이터라 부른다.

1. 코디네이터가 소비자 그룹의 조정 작업을 담당 (조정 서비스는 브로커 클러스터 조정 작업 담당)
2. 해당 소비자를 그룹에 참여시키고 파티션-2를 해당 소비자에 할당한다. (파티션 배치 정책이 있음 ex) 라운드 로빈)
3. 소비자는 마지막으로 소비한 오프셋 이후 메세지를 가져온다. (오프셋 정보는 상태 저장소)
4. 메세지를 처리하고 새로운 오프셋을 브로커에 보낸다.

### 📌 소비자 재조정
소비자가 어떤 파티션을 책임지는지 다시 정하는 프로세스다.
새로운 소비자 합류, 떠남, 장애 발생이나 파티션이 조정되는 경우 시작될 수 있다.

코디네이터가 중요한 역할인데 코디네이터는 소비자들과 통신하는 브로커 노드로 소비자의 박동(Heartbeat) 메세지를 살피고 각 소비자의 오프셋 정보를 관리한다.

[134. 소비자 그룹의 코디네이터]

- 소비자 그룹의 전담 코디네이터는 그룹 이름을 해싱하면 찾을 수 있다. (= 같은 그룹의 소비자는 같은 코디네이터를 연결)
- 코디네이터는 자신에 연결한 소비자 목록을 유지 (해당 그룹의 새 리더 선출)
- 새 리더는 새 파티션 배치 계획(Partition Dispatch Plan)을 만들고 코디네이터에게 전달하면 코디네이터가 그룹내 소비자에게 전달 받은 계획을 알린다.

코디네이터는 박동 신호를 감지해서 장애를 감지하고, 장애 발생시 아래와 같이 재배치 한다. 

[134. 소비자 재조정]

#### 새로운 소비자 합류
소비자-A 만 있는 상태

[135. 새로운 소비자 합류]

1. 소비자-A 는 코디네이터에게 지속적으로 박동 메세지를 보낸다.
2. 소비자-B 가 그룹에 합류 요청을 한다.
3. 코디네이터가 재조정 필요 시점으로 판단하고 모든 소비자에 통시한다. (소비자-A 는 박동 응답으로 합류 요청을 받음)
4. 모든 소비자가 그룹에 다시 합류하면 리더를 선출하고 모든 소비자에게 그 사실을 알린다.
5. 리더는 파티션 배치 계획을 생성한 다음 코디네이터에게 보내면 다른 소비자들은 파티션 배치 계획을 받아온다.
6. 소비자는 배치된 파티션에서 메세지를 가져온다.

#### 기존 소비자 이탈
소비자-A와 소비자-B 는 같은 소비자 그룹 멤버

[136. 기존 소비자의 이탈]

1. 소비자-A가 그룹 탈퇴 요청
2. 코디네이터가 소비자 재조정 필요 시점으로 판단하고 소비자-B 박동 응답에 그룹 재합류 요청

나머지 재구성 프로세스는 합류와 같다.

#### 소비자 비정상 가동 중단(장애)

[137. 소비자 장애 발생]

1. 소비자-A 가 장애가 발생해서 박동 메세지가 전달되지 못하고 이 상태가 일정 시간동안 유지되면 소비자가 사라진 것으로 판단
2. 코디네이터가 소비자 재조정 프로세스 개시

나머지 재구성 프로세스는 같다.

### 📌 상태 저장소(State Storage)

다음과 같은 정보가 저장된다.

- 소비자에 대한 파티션의 배치 관계
- 각 소비자 그룹이 각 파티션에서 마지막으로 가져간 메세지의 오프셋 (아래 그림 참조)

[138. 소비자 그룹별 마지막 소비 오프셋]

소비자 상태 정보 데이터가 이용되는 패턴

- 읽기와 쓰기가 빈번하게 발생하지만 양은 많지 않다.
- 데이터 갱신은 빈번하게 일어나지만 삭제되는 일은 거의 없다.
- 읽기와 쓰기 연산은 무작위적 패턴을 보인다.
- 데이터의 일관성이 중요하다.

이런 상태 데이터를 보관하는데 키-값 저장소를 사용하는 것이 요구사항을 충족할만한 조건이다.

### 📌 주키퍼
계층적 키-값 저장소(Hierarchical key-value store) 기능을 제공하는 분산 시스템 필수 서비스이다.

- 분산 설정 서비스 (Distributed Configuration Service)
- 동기화 서비스 (Synchronization Service)
- 이름 레지스트리 (Naming Registry)

[139. 주키퍼]

이제 브로커는 메세지 데이터 저장소만 유지하면 된다.
주키퍼가 브로커 클러스터의 리더 선출 과정을 돕는다.

### 📌 복제(Replication)
분산 시스템에서 하드웨어 장애는 흔하게 발생해서 무시할 수 없다.
디스크에 손상이나 영구적 장애가 발생하면 데이터는 사라지기 때문에 높은 가용성을 보장하기 위해 전통적으로 많이 사용된 방법이 바로 복제다.

각 파티션은 3개의 사본을 갖고, 이 사본들은 서로 다른 브로커 노드에 분산되어 있다.
짙은 색의 파티션은 리더 파티션이다.

[140. 복제]

생산자는 메세지를 파티션 리더에게만 보내고 다른 사본은 리더에서 새 메세지를 지속적으로 가져와 동기화 한다.
메세지를 동기화 한 사본의 개수가 지정된 임계값을 넘으면 리더는 생산자에게 메세지를 잘 받았다는 응답(Acknowledgement)을 보낸다.

사본을 파티션에 어떻게 분산할지 기술하는 것을 사본 분산 계획(Replica Distribution Plan)이라고 한다.

위 그림을 예로 들면

- 토픽-A의 파티션-1:
  - 리더: 브로커-1
  - 사본: 브로커-2,3
- 토픽-A의 파티션-2
  - 리더: 브로커-2
  - 브로커-3,4
- 토픽B-의 파티션-1
  - 리더: 브로커-3
  - 브로커-4,1

리더 브로커 노드가 사본 분산 계획을 만들고 메타데이터 저장소에 보관한다.

### 📌 사본 동기화(In-Sync Replicas, ISR)

[141.ISR 동작 원리]

합의 오프셋이 13일 때 리더에 2개의 새로은 메세지가 기록되었지만 아직 사본 간에 합의가 이러우진 것은 아니다.
(합의 오프셋의 의미는 오프셋 이전에 기록된 모든 메세지는 이미 ISR 집합 내 모든 사본에 동기화가 끝났다는 것이다.)

사본-2,3 은 리더 상태를 동기화 하여 ISR 되어 있지만 사본-4는 충분히 따라잡지 못하였으므로 아직 ISR이 아니다.
생산자가 보낸 어떤 메세지도 소시하지 않는 가장 안전한 방법은 생산자에게 메세지를 잘 받았다는 응답을 보내기도 전에 모든 사본을 동기화 하는 것이다.
어느 사본 하나라도 동기화를 신속하게 처리 못하면 파티션 전부가 느려지거나 못 쓰게 되는 일이 벌어질 수 있다.

#### ACK 

[142]

ACK=all: 생산자는 모든 ISR 이 메세지를 수신한 뒤 ACK 응답을 받는다.
  - 가장 느린 ISR의 응답까지 기다려 시간이 길다.
  - 메세지 영속성 측면에서는 가장 좋다.

[143]

ACK=1: 리더가 메세지를 저장하고 바로 ACK를 받는다.
  - 데이터 동기화를 기다리지 않아 지연 개선
  - 리더 장애시 사본에 반영되지 않아 복구 불가능
  - 낮은 응답 지연을 보장하는 시스템에 적합

[144]

ACK=0: 생산자는 응답을 기다리지 않는다.
  - 낮은 응답 지연을 위해 메세지 손실을 감수

#### 소비자에서 리더가 메세지를 읽어가도록 하지 않는 이유는?

- 설계 및 운영이 단순
- 특정 파티션의 메세지는 같은 소비자 그룹 안에서는 오직 한 소비자만 읽어갈 수 있어 리더 사본에 대한 연결은 많지 않음
- 인기 있는 토픽이 아니면 리더 사본에 대한 연결의 수는 많지 않음
- 인기 있는 토픽이라면 파티션 및 소비자 수를 늘려 규모를 확장

데이터 센터 같이 다른 지역이라고 할 때는 리더 사본에서 메세지를 가져가는 것이 읽기 성능이 안좋을 수 있다.
이런 케이스는 가까운 ISR 사본에서 메세지를 읽는게 좋을 수 있다.
(파티션 담당 리더는 사본들이 메세지를 어디까지 가져갔는지 추적하고 ISR 목록을 관리)

브로커의 결함 내성을 높이기 위해서 고려할 사항

- 지연성과 안정성의 균형: 메세지가 성공적으로 합의(Committed) 되었다고 판단하려면 얼마나 많은 사본에 메세지가 반영되어야 하는지
- 파티션의 모든 사본을 같은 노드에 두면 장애 발생시 해당 파티션 완전 소실
- 사본은 여러 데이터 센터에 분산이 안전

위 처럼 브로커 노드가 추가되거나 삭제될 때 사본을 재배치할 수 있지만 그 보다 나은 방법으로 브로커 컨트롤러로 하여금 한시적으로
시스템에 설정된 사본 수보다 많은 사본을 허용하는 것이다.

1. 최초 구성

- 토픽-A의 파티션-1
  - 리더: 브로커-1

  - 리더: 브로커-2
  - 사본: 브로커-1,3

2. 브로커-4가 추가되면서 브로커 컨트롤러는 사본 분산 계획을 변경한다.

  - 리더: 브로커-1

  - 리더: 브로커-2

3. 브로커-4의 사본이 리더의 상태를 완전히 따라잡으면 브로커-1에 있는 불피요한 사본은 삭제

- 토픽-A의 파티션-1
  - 리더: 브로커-1
  - 사본: 브로커-2,3
- 토픽-A의 파티션-2
  - 리더: 브로커-2
  - 사본: 브로커-3,4

브로커 추가 도중에 발생할 수 있는 데이터 손실을 피할 수 있고, 브로커 제거할 때도 비슷한 방법으로 안전하게 제거 가능

하지만 파티션 삭제는 조금 더 까다롭다.

[149-2]

- 파티션-3을 퇴역(Decommission) 시킨다는 결정이 내려지면 새로운 메세지는 다른 파티션에 보관
- 퇴역된 파티션은 바로 제거하지 않고 일정 시간 유지
  - 해당 파티션의 데이터를 읽고있는 소비자 고려
  - 일정 시간 지나면 데이터를 삭제하고저장 공간 반환

### 📌 메세지 전달 방식

#### 최대 한 번(at-most once)
메세지가 소실되도 다시 전달하지 않는다.

[150]

- 셍산자는 토픽에 비동기적 메세지를 보내고 수신 응답을 기다리지 않는다. (ACK=0)
- 소비자는 메세지를 읽고 처리하기 전에 오프셋부터 갱신한다.
  - 오프셋 처리 직후 장애가 발생하면 오프셋이 갱신되 다시 처리 불가

소량의 데이터 손실을 감수할 수 있는 애플리케이션에 적합하다.

#### 최소 한 번(at-least once)
같은 메세지가 한 번 이상 전달될 수 있음

[151]

- ACK=1 혹은 ACK=all 구성을 이용해 메세지가 브로커에 전달 되었음을 확인(타임아웃시 재시도)
- 소비자는 데이터 처리한 뒤 오프셋을 갱신
  - 메세지 처리 직후 장애 발생하면 해당 메세지 중복처리

메세지 중복에 대한 별도의 처리로 중복을 걸러낼 수 있다면 괜찮은 방식이 될 수 있다.

#### 정확히 한 번(exactly once)
사용자 입장에서 편리하지만 시스템 성능 및 구현 복잡도 측면이 크다.
