# 지표 모니터링 및 경보 시스템

## 1단계: 문제 이해 및 설계 범위 확정
여느 다른 챕터와 같이 요구사항 정의부터 시작한다.
면접관이 인프라 지표에 관심 있는데 웹 서버 에러 로그나 엑세스 로그에 초점을 두는 것은 곤란하다는 말을 덧 붙이면서 구체적인 요구사항 정의를 시작한다.

❌ 해당 line 블로그 글로 정리 하지말고 참고해줘: 밑에 요구사항과 대답은 다른 챕터의 양식에 맞춰서 해줘 질문과 답변은 정리 해두니까 

- 시스템 설계가 목적인가 아니면 SaaS 같은 제품을 설계 하는것인가? => 회사 내부
- 어떤 지표를 수집하는가? CPU부하, 메모리 사용률, 디스크 사용량(저수준 OS 사용률 지표), 초당 요청 수(RPS), 웹 서버 프로세스 개수 But 사업 지표는 아님

- 경보는? => 이메일, 전화, 페이지듀티(Page Duty), 웹훅(Webhook)
- 에러, 엑세스 로그 x / 분산 시스템 추적 x

### 비기능 요구사항

- 규모 확장성: 늘어나는 지표와 경보의 양에 맞춰 확장 가능해야함
- 낮은 응답 지연: 대시보드(dashboard) 와 경보(alert)를 신속하게 처리할 수 있도록, 질의(query)에 대한 낮은 응답 지연을 보장해야한다.
- 안정성: 중요 경보를 놓치지 않도록
- 유연성: 변하는 기술들이 쉽게 통합될 수 있도록

로그 모니터링과 분산 시스템 추적에 대한 요구사항은 고려하지 않는다.

❓ 분산 시스템 추적: 서비스에 대한 요청이 분산 시스템 내부에서 어떻게 흐르는지 추적할 수 있는 시스템

## 2단계: 개략적 설계안 제시 및 동의 구하기

### 기본적 사항

- 데이터 수집(data collection): 여러 출처로 지표 데이터 수집
- 데이터 전송(data transmission): 수집한 지표 데이터를 모니터링 시스템으로 전송
- 데이터 저장소(data storage): 데이터 정리 및 저장
- 경보(alerting): 데이터 분석 후 이상 징후 감지 및 경보 (다양한 채널로 경보)
- 시각화(visualization): 데이터 차트나 그래프 등으로 제공 (시각적으로 보여주면 패턴, 추이, 문제점 파악이 쉬움)

### 데이터 모델
지표 데이터는 통상 시계열(time series) 데이터 형태로 기록한다.(타임스탬프가 붙은 형태)
시계열 각각에는 고유한 이름이 붙고, 선택적으로 레이블(label) 이 붙는다.

[163-1]

시계열 데이터 ㅎㅇ식은 행 프로토콜(line protocol) 을 따르고 있다.

❌ 밑에는 시계열 데이터 표

지표 이름 | 문자열
태그/레이블 집합 | <키:값> 쌍의 리스트
지표 값 및 그 타임스탬프의 배열 | <값, 타임스탬프> 쌍의 배열

### 데이터 접근 패턴

[165]

매일 천만 개 운영 지표가 기록되고 트래픽은 단연 쓰기가 압도적이다.

### 데이터 저장소 시스템

지금 설계하는 시스템은 범용 의 저장소 시스템은 추천하지 않는다.
범용적인 RDB 의 경우 많은 양의 쓰기 연산이 지속적으로 발생하는 환경에서는 좋은 성능을 보이지 못한다.
NoSQL 도 시계열 데이터를 효과적으로 저장하려면 확장이 용이한 스키마 설계를 해야한다.

이미 시장에 시계열 데이터를 위한 최적화된 저장소 시스템은 많다.
시계열 데이터 분석에 적합한 쉬운 질의 인터페이스도 있고, 보관 기간 설정이나 데이터 집계(Aggregation) 기능을 제공하는 제품도 있다.

8CPU 코어 32GB 램을 갖춘 InfluxDB 서버 한 대로 초당 250,000회의 쓰기 연산 처리가 가능하다.
우리가 여기서 얻고자 하는건 이런 특수한 데이터베이스 내부 구조를 이해하는것이 아니라 지표 데이터를 시계열 데이터베이스에 저장할 수 있음을 설명하는 것이다.


### 개략적 설계안

[168]

- 지표 출처(Metrics Source): 지표 데이터가 만들어 지는 곳(앱, DB, MQ 등)
- 지표 수집기(Metrics Collector): 지표 데이터 수집 및 기록
- 시계열 데이터베이스(Time-series DB): 시계열 데이터 형태로 보관하는 저장소(시계열 데이터 특화)
- 질의 서비스(Query Service): 보관된 데이터를 질의하고 가져오는 과정을 돕는 서비스
- 경보 시스템(Alerting System): 경보를 받아야하는 대상들에 알림 전송
- 시각화 시스템(Visualization System): 지표를 그래프/차트로 시각화

## 3단계: 상세 설계

### 지표 수집
Counter 나 CPU 사용량 같은 지표를 수집할 때는 때로 데이터 소실 감안한다.

[170-1]

#### 풀 모델

아래는 HTTP 기반 풀 모델을 이용하는 지표 수집 흐름

[170-2]

이러한 접근 방법은 지표 수집기가 데이터를 가져올 서비스 목록을 알아야 한다.
지표 수집기에 모든 서비스 엔드포인트 DNS/IP 정보를 담은 파일을 두면 간단하지만 서버가 수시로 변경되는 대규모 서비스 환경에는 적용이 어렵다.

[171-1]

이런 경우 etcd나 Apache ZooKeeper 같은 서비스 탐색(Service Discovery) 기술을 활용하면 해당 문제를 어느정도 해결할 수 있다.
SDS dㅔ는 언제 어디서 지표를 수집하면 되는지에 관한 설정 정보를 기록한다.

[171-2]

1. 지표 수집기는 SDS 에서 서비스 엔드포인트 설정 메타데이터 목록을 가져온다.
   지표 수집 주기(pulling interval), IP 주소, 타임아웃(timeout),재시도 인자(retry parameter) 등이 기록되어 있다.
2. HTTP 엔드포인트에서 지표 데이터를 가져온다.
3. 지표 수집기는 서비스 엔드포인트 목록의 변화를 통지 받기 위한 변경 이벤트 알림 콜백을 서비스 탐색 컴포넌트에 등록해 주기적으로 목록을 다시 가져온다.

수천 대 서버가 만들어 내는 지표 데이터를 수집하려면 지표 수집기 서버 한대로 부족하다.
지표 수집기 풀을 만들어야 하는데 같은 출처에서 중복 데이터를 수집할 수 있으니 안정 해시 링(consistent hash ring) 을 사용 한다면 특정 지표 서버의 지표 데이터는 항상 하나의 수집 서버가 처리함을 보장한다.

[173-1]

#### 푸시 모델
웹 서버나 DB가 직접 지표 수집기에 지표 데이터를 전송하는 모델이다.

[173-2]

푸시 모델의 경우 모니터링 대상 서버에 통상 수집 에이전트라고 부르는 소프트웨어를 설치하고, 지표 데이터를 받아 모은 다음 주기적으로 수집기에 전달한다.
수집기가 막대한 트래픽으로 처리하지 못하면 에이전트는 내부 소규모 버퍼에 데이터를 일시적으로 보관했다 재전송한다.
에이전트가 위치한 서버 클러스터가 자동 규모 확장(Auto Scaling)이 설정되어 있다면 서버가 동적으로 추가되거나 삭제되는 과정에서 데이터 소실도리 수 있다.

[174]

이런 일을 방지하기 위해서는 지표 수집기 서버 클러스터 자체도 자동 규모 확장이 가능하도록 구성하고 앞에 LB 를 두는 방법도 있다.

#### 풀 vs 푸시 모델의 장단점 비교
풀 모델 유명 사례는 프로메테우스(Prometheus), 푸시 모델은 아마존 클라우드와치(CloudWatch) 등이 있다.

| 항목 | 풀 모델 | 푸시 모델 | 유리 |
|---|---|------------------------------------------------------|---|
| 손쉬운 디버깅 | `/metrics` 엔드포인트가 있어 언제든 지표 확인 가능 (랩톱에서도 가능) | - | 풀 |
| 상태 진단 | 풀 요청에 응답이 없으면 곧바로 서버 장애로 판단 | 지표가 안 들어오면 네트워크 장애인지 서버 장애인지 구분이 어려움 | 풀 |
| 생존 기간이 짧은 프로세스 | 지표를 가져가기 전에 프로세스가 끝날 수 있음 (push gateway를 두면 해결) | 프로세스가 끝나기 전에 직접 보낼 수 있음 | 푸시 |
| 복잡한 네트워크 구성 (방화벽 등) | 모든 `/metrics` 엔드포인트에 접근할 수 있어야 함. 데이터센터가 여러 개면 네트워크를 세심하게 설계해야 함| 수집기를 로드밸런서와 오토스케일링 클러스터로 구성하면 어디서 오는 지표든 받을 수 있음 | 푸시 |
| 성능 | 주로 TCP | 주로 UDP라서 전송 지연이 더 낮음 (반론: TCP 연결 오버헤드는 전송 비용에 비해 작음) | - |
| 데이터 신빙성 | 수집 대상 서버 목록이 미리 정해져 있어 믿을 수 있음 | 누구나 데이터를 보낼 수 있음. 허용 서버 목록을 두거나 인증을 강제하면 해결 | 풀 |

### 지표 전송 파이프라인의 규모 확장

[176]

기존 설계를 보면 엄청난 지표 데이터 양을 처리해야 하는데 시계열 DB 가 장애가 생기면 데이터 손실이 발생할 가능성이 있는 구조다.

[177-1]

앞에 큐를 두면 해당 문제를 어느정도 해소할 수 있다.
큐 시스템에서 전송 받으면 스트림 처리 서비스가 해당 데이터를 받아 시계열 DB에 저장한다.

- 카프카는 고도로 안정적이고 규모 확장성이 뛰어난 분산 메세지 플랫폼
- 데이터 수집, 처리 컴포넌트 결합도를 낮춘다.
- DB 장애시 데이터 소실을 막을 수 있다.

### 카프카를 통한 규모 확장

파티션 메커니즘을 사용하면 다양한 방법으로 확장 가능

- 대역폭 요구사항에 따라 파티션의 수를 설정
- 어떤 지표를 어느 파티션에 배치할지 결정하면 소비자는 지표 이름에 따라 데이터 집계
- 태그/레이블에 따라 지표 데이터를 더 세분화한 파티션으로 나눔
- 중요 지표가 처리될 수 있도록 우선순위 선정

### 카프카의 대안

상용 규모의 카프카 시스템 구축은 쉽지 않다.
시장에는 큐 없이도 대규모 데이터 처리가 가능한 모니터링 시스템이 있다. (네트워크 장애가 발생해도 쓰기 연산 가용성 유지)

### 데이터 집계 지점

- 수집 에이전트가 집계하는 방안: 클라이언트에 저장된 수집 에이전트는 복잡한 집계 로직 지원이 어렵다.
- 데이터 수집 파이프라인에서 집계하는 방안: ❓ 어떤걸 말하고 싶은거지?
- 질의 시에 집계하는 방안: 질의가 필요할 시간 구간에 맞게 집계하는 방법으로 데이터 손실 문제는 없으나 질의와 같이 집계 계산이 이루어져 속도가 느리다.

### 질의 서비스
질의 서버 클러스터 형태로 구현되며, 시각화 또는 경보 시스템에서 접수된 요청을 시계열 DB를 통해 처리하는 역할 담당
질의 처리 서비스를 두면 클라이언트(시각화 or 경보 시스템)와 시계열 DB 사이의 결합도를 낮출 수 있어 DB 교체도 자유롭다.

#### 캐시 계층
DB 부하를 낮추고 질의 서비스 성능을 높이는 방법으로 캐시 도입

[179]

#### 질의 서비스를 두면 곤란한 경우
시장에서 널리 사용되는 시계열 DB의 연동을 처리하는 플러그인들은 이미 갖추고 있는 경우가 많아 별도의 캐시를 도입할 필요 없는 케이스도 고려사항

#### 저장 용량 최적화
지표 모니터링 시스템에 저장할 데이터의 양이 많기 때문에 최적화가 필요하다.

##### 데이터 잌노딩 및 압축

[181]

타임스탬프 하나를 온전히 표현하는데 32비트가 필요하지만 10을 표현하는데 4비트만 필요하다.

##### 다운샘플링(Downsampling)

데이터의 해상도를 낮춰 저장소 요구량을 줄이는 기법이다.
보관 기간은 1년이므로, 낡은 데이터는 해상도를 줄여도 된다.

- 7일 이내: 적용x
- 30일 이내: 1분 해상도로 낮춰서 보관
- 1년 이내: 1시간 해상도로 낮춰서 보관

##### 냉동 저장소(Cold Storage)

비활성 상태 데이터를 보관하는 장소
